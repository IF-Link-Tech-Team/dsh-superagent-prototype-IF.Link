# IFLink Team Agent 需求说明

## 一、背景

IFLink 是一个 AI 创客与科技交流社区。团队日常工作横跨运营、活动、产品、技术、优质内容，以及第二课堂、iflight 比赛、中转站等不同业务线和项目组，工作信息分布在飞书、GitHub、微信等平台。

团队希望逐步建设一个共用的 **IFLink Team Agent**。它不是一个只回答问题的聊天机器人，也不是若干彼此孤立的 Session，而是一个**非常了解团队各业务线、能够持续学习并主动完成真实工作的全能 AI 同事**。

## 二、核心定位

Team Agent 应当成为团队的长期协作者：

- 理解团队的组织、项目、业务、成员和工作方式；
- 拥有连续、完整且可调用的团队上下文；
- 能在飞书等真实工作环境中沟通、协作和交付；
- 能同时推进多个项目，并协调不同业务线之间的关系；
- 能从团队实践中持续学习，把经验沉淀为可复用的能力；
- 能长期在线、持续恢复，并逐步提高自主完成工作的范围。

**短期目标：**成为一个 24 小时在线、可靠、懂团队的 Agent 同事。

**长期目标：**成为团队 AI-native 工作方式的重要枢纽，能够协调并驱动团队工作，逐步承担大部分真实任务。

## 三、核心需求

### 1. 全面理解团队与各业务线

Team Agent 应当持续了解：

- 各职能组和项目组的职责、目标、项目及相互关系；
- 各项目的历史背景、当前状态、关键决策、负责人、待办和风险；
- 团队成员的角色、偏好、工作习惯和协作方式；
- 团队已有的文档、代码、Skill、规范、经验和最佳实践。

面对任何业务线的问题，它都应尽量结合团队整体情况理解和回应，而不是把每个群、每个项目都当作互不相干的新对话。

### 2. 连续、可召回的团队上下文与长期记忆

Team Agent 应当具备跨会话、跨平台、跨时间的连续上下文：

- 同一件事在飞书、GitHub、微信之间推进时，不被割裂成多个任务；
- 能记住重要决策及其原因、项目进展、未完成任务、交付结果和后续修正；
- 能区分长期有效的事实、不断更新的项目状态、一次性事件和可复用的方法；
- 能根据当前工作主动找到相关历史，而不是依赖成员重复背景或提供精确的任务编号；
- 能随着新决策和新进展更新旧记忆，避免把过期信息当作当前事实。

团队上下文应当整体共享，但执行具体任务时只关注相关信息，避免不同项目的执行细节相互干扰。

### 3. 以飞书为主要沟通与协作入口

Team Agent 应当自然地参与飞书中的团队工作：

- 被 @ 时能够回答问题、接受任务、补充上下文并继续推进；
- 没有被 @ 时，也能在确有价值的情况下主动回复、提醒或介入；
- 能主动发现待办、风险、时间节点和需要人工决策的事项；
- 能在适当情况下直接完成工作，而不只是给出建议；
- 群聊表达应简洁、明确、低打扰，普通讨论保持安静；
- 需要人工决策时提出具体问题，有结果时清楚交付，无法完成时诚实说明。

### 4. 跨平台连续协作

Team Agent 需要连接团队的主要工作平台：

- **飞书：**日常沟通、任务发起、团队协作、提醒、审批与结果交付；
- **GitHub：**项目、代码、Issue、Pull Request、文档和 Skill 等长期资产；
- **微信：**通过 ClawdBot 插件转发关键聊天记录，将社区反馈和运营信息纳入团队上下文。

同一项工作可以从微信反馈开始，在飞书中讨论和决策，再在 GitHub 中交付，最后回到原沟通渠道同步结果，整个过程保持连续。

### 5. 多业务线、多任务并发

Team Agent 应当能够同时服务多个职能组和项目组：

- 不同任务可以并行推进，不因一个长任务而阻塞其他消息和工作；
- 每个任务保持独立、专注的执行上下文；
- 跨任务共享必要的团队事实、项目背景和关键决策；
- 当多个任务涉及同一项目、资源或目标时，能够识别关系并协调冲突；
- 新增业务线或项目组时，可以纳入同一个 Team Agent，而不必重新建立一套孤立体系。

### 6. 全能的真实工作能力

Team Agent 不仅要会沟通，还要能够完成团队中的多类型工作，包括但不限于：

- 信息检索、资料整理、总结归纳和知识问答；
- 文档、纪要、周报、方案、内容和项目材料；
- 运营跟进、活动筹备、时间节点提醒和项目协调；
- 社区反馈整理、问题定位和跨团队信息同步；
- 产品分析、技术调研、代码修改、Issue 和 Pull Request 工作；
- 任务拆解、进度跟踪、风险提示和结果复盘。

它应当以实际交付为目标，能够根据任务需要调动不同能力，而不是只提供建议或停留在对话层面。

### 7. 主动协作与逐步扩大自治

Team Agent 应当从“等待指令”逐步发展为“主动推动工作”：

- 从完成明确指派的任务开始；
- 逐步能够主动提醒、起草、跟进和完成边界清晰的工作；
- 长期能够发现工作缺口、拆解目标、协调资源并推动项目闭环；
- 自主性应与可靠性相匹配，逐步扩大，而不是一开始就无边界放开；
- 涉及重要决策、对外承诺或高影响操作时，应当保留人工确认和接管能力。

### 8. 持续学习与团队智慧沉淀

Team Agent 应当从真实协作中持续学习：

- 从成功任务、失败尝试、人工纠正和重复工作中提炼经验；
- 记录并更新团队偏好、项目知识、工作规范和有效方法；
- 把反复使用、经过验证的流程逐步整理成可复用的 Skill；
- 让团队的优秀实践不只存在于聊天记录或个人经验中，而是成为团队共享能力；
- 能区分一次性任务记录与长期有效的方法，避免简单堆积历史信息；
- 随着使用不断变得更了解团队、更少重复提问、更少重复犯错、更稳定地完成任务。

最终形成“工作产生经验、经验沉淀为能力、能力再用于工作”的持续循环。

### 9. 长期在线、可恢复、可自愈

Team Agent 应当运行在团队当前的 Linux 机器上并保持 Always On：

- 长期在线，能够持续接收消息和推进任务；
- 进程重启或异常后，能够恢复原有上下文、任务和待办；
- 遇到网络、模型或外部平台的临时故障时，能够重试和恢复；
- 避免因恢复而重复执行工作、重复发送消息或丢失关键状态；
- 团队能够查看其运行状态，并在需要时暂停、接管或停止。

### 10. 可信、可控、可负责

Team Agent 的自主行为应当建立在清晰的团队边界之上：

- 不同成员、群组、项目和动作具有相应的权限与授权范围；
- 外部消息和转发内容不应被直接视为高权限指令；
- 重要操作应可确认、可追踪、可审计、可撤销；
- 团队始终能够了解它做了什么、为什么做、结果如何；
- 团队对它的对外表达和实际行为保留最终责任与控制权。

## 四、典型工作状态

- 运营组需要周报时，Team Agent 能汇集不同项目的进展，识别待办与风险，并在适当时间提醒相关人员。
- 活动组筹备活动时，Team Agent 能延续以往活动经验，协助方案、分工、材料、提醒和复盘，并把有效做法沉淀下来。
- 微信中的社区反馈可以进入团队上下文，经飞书讨论后形成任务，在 GitHub 完成交付，再由 Team Agent 向相关人员同步结果。
- 技术组、产品组和其他项目组可以同时推进不同任务，既共享团队整体背景，又保持各自工作的专注与连续。
- 当某类工作重复出现时，Team Agent 能复用已有经验，并逐步把它形成团队认可的 Skill。

## 五、期望的最终状态

Team Agent 应当逐步做到：

> **懂团队、记得住、找得到、能沟通、能并发、能执行、会学习、一直在线。**

它既是团队成员的统一协作入口，也是团队上下文和经验的长期承载者，最终成为推动 IFLink 团队持续 AI-native 化的重要伙伴。
