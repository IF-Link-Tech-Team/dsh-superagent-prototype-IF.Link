# 模型 Token 消耗：审计与压缩

更新：2026-11-12 · 范围只算 Team Agent 运行时（router + worker + worker 子代理），不含我们的开发会话

## 一、结论

- 8 天（11/04–11/12）**22.3 亿 token**，其中 **65% 花在 router 一条永不更换的会话上**。
- router 每处理一次事件要读 42.8 万上下文、只输出约 100 token，**输入:输出 = 6600:1**。
- 按 DeepSeek 官方牌价折算是 **121 元**（约 15 元/天、1.59 元/工单），其中 73% 落在中转站、27% 走自建 vLLM。
- 已把 router 的压缩阈值从"窗口 80%（80 万）"降到 **12 万触发 / 保留 2.4 万**，实测 597k → 61.6k。

## 二、口径

数据源：`~/.dsh/sessions/**/session.v4.jsonl.zstd` 每条 `assistant/message` 的 `data.usage`。
DSH 的 `totalTokens = 未命中输入 + 缓存读 + 输出`（19,403 条全部成立），所以"输入"是扣掉缓存的那部分。

计价：官方 `deepseek-flash`（文档写明就是 DeepSeek-V4.1-Flash-1017），单位元/百万 token：

| | 空闲 | 高峰 |
|---|---:|---:|
| 输入（缓存命中） | 0.02 | 0.04 |
| 输入（缓存未命中） | 1 | 2 |
| 输出 | 4 | 8 |

高峰 = 北京时间周一至周五 9:00–12:00、14:00–18:00。**按每条调用的时间戳逐条判峰谷**，不是用平均价。

## 三、总量与结构

| 组件 | 调用 | 缓存读 | 未命中 | 输出 | 合计 | 占比 |
|---|---:|---:|---:|---:|---:|---:|
| router | 3,398 | 1,438.5M | 17.0M | 0.34M | **1,455.8M** | 65.3% |
| worker | 6,487 | 714.5M | 14.0M | 4.0M | **732.5M** | 32.9% |
| worker 子代理 | 982 | 38.4M | 1.7M | 0.8M | 41.0M | 1.8% |

稳定期约 3.2 亿 token/天；11/09 峰值 7 亿。

## 四、根因：router 是一条永生的会话

router 从 11/05 起只有一条会话，1,738 轮、3,398 次调用，上下文从 1.75 万一路涨到 **80 万**：

```
11-05 平均 3.8 万 → 11-08 38 万 → 11-09 60.8 万 → 11-12 57.5 万
```

- 8 天里只压缩过 1 次（11/10 12:03，80.0 万 → 26.4 万，摘要本身只有 1,570 token）。
- 75% 的调用发生在上下文 >30 万时，吃掉 89% 的 router token。
- 输入:输出 6600:1 —— 花的钱几乎全在"把旧历史再读一遍"，不在生成。

拆开看 router 在做什么：1,475 次 `orchestrator_route`（研判）+ 338 次 `orchestrator_reply`（在群里说话）。
它不只是"分配"：要判断新单/并单（所以读工单列表）、要起草标题和 acknowledgement、要写群消息
（还被飞书 100 字限制打回重写过）、还要中转 worker 的结果。

## 五、缓存命中率说明了什么

总命中率 **98.53%**（2,191.4M 缓存读 / 32.8M 未命中），单次调用的中位数 99.46%。

但未命中的构成是：

| 来源 | 次数 | token | 占比 |
|---|---:|---:|---:|
| 会话首次调用 | 115 | 1.1M | 3.5% |
| 空闲 >10 分钟后的调用 | 176 | 17.4M | **53.1%** |
| 正常增量 | — | 14.2M | 43.4% |

按间隔分桶，命中率断崖：<2 分钟 99.33%、2–10 分钟 99.45%、10–60 分钟 83.63%、>60 分钟 **35.88%**。

结论：命中率已经贴着物理上限，**真正贵的是"长上下文 × 冷启动次数"**。按 1:10 的单价加权，
未命中占输入成本的 13%（其中闲置过期 6.9%）——所以把上下文压小，比抠命中率有效得多。

## 六、钱花在哪

```
缓存命中输入  2,191.4M  (98.5% 的量)   ¥54.23  (44.9%)
缓存未命中        32.8M  (1.5%)        ¥41.22  (34.1%)
输出              5.17M  (0.23%)       ¥25.40  (21.0%)
```

**输出只占 0.23% 的量却吃掉 21% 的钱**（单价是缓存命中的 200 倍）。

单位经济：¥15.11/天、¥1.59/工单（worker 侧 ¥0.81）、**router 每轮 ¥0.034**。

## 七、改了什么

`cordis.patch.yml` 的 router preset 加了压缩参数（worker 不动）：

```yaml
- id: compaction-basic
  config:
    thresholdRatio: 0.12     # 12 万触发（默认 0.8 × 1M = 80 万）
    retainTokens: 24000      # 保留最近 2.4 万原文
```

选这两个数的依据：router 历史增长约 7K/小时（19 条消息/小时），2.4 万 ≈ 最近 3.5 小时的原文，
12 万 ≈ 14 小时的跨度；而系统提示 + 工具定义本身就占 1.75 万，阈值不能贴着它。

实测（11/12 23:18）：597,162 → 61,628，之后稳定在 6–8 万缓慢增长。

**代价要写清楚**：压缩请求要把整段上下文重放一遍，如果缓存已冷，就是全价。第一次冷压读了 663,916 token，
约 **¥0.67**；隔夜后第一次压缩都是这个量级。热压约 ¥0.01。以后每次压的是 12 万，冷压约 ¥0.12。

## 八、下一步（未做）

按性价比排：

1. **闲聊不该进模型**：3,648 条决策里 92.7% 是 ignore，1,738 次研判只出 76 个工单（4.4%）。
   线程里已有工单 + 消息里没有请求动词 + 没 @ → 直接记 ignore，不进研判。
2. **显式 @ 直连**：`explicitRouted` 已经有 70 次——「@bot + 明确动作」不需要模型完整研判，
   直接建单让 worker 理解任务，router 只出标题。
3. **把"说话"和"判断"拆开**：现在同一条会话既判 18 条消息、又要在 100 字内润色群文案、还要处理发送失败重写，
   上下文互相污染。

## 九、怎么复算

扫描器逻辑（约 40 行，本体不入库）：遍历 `~/.dsh/sessions/*/*/session.v4.jsonl.zstd`，流式解压，
只取 `{"type":"assistant/message"` 开头的行，从 `"usage":` 处 `raw_decode` 取用量、从 `"source":{"kind":"model"`
取 provider/model，按 `policy.gate` 里的组件归属分类。8 天全量扫描约 2 秒。
