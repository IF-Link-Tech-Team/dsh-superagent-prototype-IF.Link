# Policy 规则草稿

> 三条规则，对应"记得住、找得到、有人找人做事"。
> 启用后即进入 `auto`，会真实建工单并在群里发言，请确认后再写。

## 规则一：历史查询

```yaml
id: history-lookup
name: 历史查询
enabled: true
```

**instruction：**

```text
群里有人询问过去发生过的事、以前做过的决定、某个项目的进展，或某个说法的出处，而答案需要翻聊天记录、飞书文档或会议纪要才能给出。

交付物：一段带来源的回答，说明依据哪份文档、哪个群、哪段时间的对话。

不算：征求意见（如"你觉得应该吗"）、需要做判断而不是找事实的问题、已经有人回答过的问题、询问未来计划的问题。

依据要求：询问对象必须明确——具体项目、具体事件、具体文档或具体说法。指代模糊（"那个事"）且在上下文里找不到对应物时，不算。
```

**风险：低。** 只是查资料，查错了也好纠正。

## 规则二：决策记录

```yaml
id: decision-log
name: 决策记录
enabled: true
```

**instruction：**

```text
群里明确拍板了一件事：定了方案、定了负责人、定了时间节点，或者否掉了一个方向，但没有留下记录。

交付物：一条结构化记录，包含决定内容、决定时间、做决定的人、当时的理由（如果讨论里说过）。写进团队记忆或文档，并在原群用一句话说明记了什么。

不算：还在讨论中、结论未定、只是有人提议、已经有人记录过的内容。

依据要求：必须能从对话里指出明确的决定语句，以及做出这个决定的人。
```

**风险：低。** 只是记录，不替人做决定。

## 规则三：无人认领的请求

```yaml
id: unclaimed-request
name: 无人认领的请求
enabled: true
```

**instruction：**

```text
群里有人提出需要有人做的一件事，但没有指定由谁来做。例如"谁能整理一下""这个谁来跟进""需要有人对接一下""有没有人帮忙看下"。

交付物：能直接做掉的小事就直接做，并说明结果；需要多步的，拆成一条明确待办（做什么、建议谁做、什么时候要），发到原群。

不算：已经明确点名某人的请求、纯提问、纯讨论、需要先做设计决策的事、需要多人协调排期的事、涉及对外承诺或钱与合同的事。

依据要求：必须能从对话里指出具体要做的事，以及它指向的对象。
```

**风险：中。** 容易多管闲事，尤其判断"该谁做"的时候。

## 三者的边界

| 情况 | 命中哪条 |
|---|---|
| "上次那个 workshop 是谁负责的？" | 历史查询 |
| "那就定 11 月 20 号办，我对接场地" | 决策记录 |
| "谁能整理一下报名表" | 无人认领的请求 |
| "我觉得这个方案有点问题" | **都不命中**（无请求意图） |
| "我们要不要办个活动" | **都不命中**（需设计决策） |

最后两行是有意的：前者交给被 @ 时的对话，后者本来就不该由它拍板。
