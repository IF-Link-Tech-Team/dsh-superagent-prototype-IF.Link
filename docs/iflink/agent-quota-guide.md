# 让自己的 Agent 少烧额度：一份通用清单

写给团队里各自搭 Agent 的人。**不讲具体代码**——大家用的框架不一样，这里只讲"该找什么、怎么验收"。
我们踩过的坑在最后一节，可以直接对照。

## 一、先量，再改

没有计量就没有优化。动手前先回答三个数：

1. **日预算是多少**：平台总额度 ÷ 30。飞书免费版是 100 万次/月，也就是 3.3 万次/天。
2. **现在实际用了多少**：平台管理后台的调用统计，或者网关日志。**别用自己的日志估**。
3. **这些调用里，多少是"拉"的，多少是"推"的**。这是后面所有优化的关键分母。

三个数拿不出来，先别改代码——你没法知道改完是变好还是变坏。

## 二、四类最常见的浪费

按我们观察到的频率排：

**1. 全量重扫。** 定时任务每分钟/每几分钟把所有群、所有话题、所有文档扫一遍。
正确做法是**事件驱动 + 分级兜底**：收到推送就只处理那一条；全量扫描退到小时级，作为"推送可能丢了"的保险。

**2. 冷对象永不退休。** 一个半年前的话题，每两小时还被读一遍，只为了确认它仍然安静。
加一条规则：**多久没动静就不再主动读**。我们的取值是 12 小时（记录保留两周，但只在 12 小时内有消息时才去读）。
注意 7 天这种"看着安全"的阈值往往等于没优化——我们 125 个话题里有 122 个在 7 天内都活跃过。

**3. 上下文无界。** Agent 的主会话如果永不更换，每条新消息都要把前面几十万 token 重读一遍。
表现是"输入:输出 = 几千比一"。**设压缩阈值，或者定期开新会话**（带一份摘要过去）。

**4. 兜底比主路径还贵。** 推送已经覆盖 99% 的消息，轮询还在每分钟全量拉。先确认推送的覆盖率，
再决定兜底要多勤。

## 三、改的时候守三条

**1. 默认值必须有测试断言。**
我们最惨的一次：把轮询改成小时级，提交、构建、重启、自检全绿，然后额度继续被烧——
原因是节奏常量的默认值没乘 60,000，全部被当成毫秒，**每一轮都在全量扫**，比改之前还多花三成。
环境变量没设置时走的那条路径，几乎没人测。

**2. 兜底不能被优化掉。**
"冷了就跳过"如果用的是内存里的活跃度标记，**重启后全部清空**，而那些标记恰好是用来判断'该补扫了'的——
最需要补偿的那一轮反而全跳过。判断要落在持久化的时间戳上，并且**断线补偿那轮必须强制全量**。

**3. 一次只改一个变量，改完立刻复测。**
否则你不知道是哪一处起了作用。

## 四、怎么验收（别用自己的日志）

自己打的日志只能证明"我打印了"，不能证明"调用变少了"。可靠的指标来自被观测对象之外：

- 平台管理后台的调用计数（看斜率，不是看总数）
- 网关/代理的请求数
- 进程数：我们自己数服务每秒派生的子进程（`/proc/<pid>/task/*/children`），同一方法前后对比最直观
- 模型侧：账单项，不是 token 估算

**健康检查全绿 ≠ 省钱。** 我们的额度是烧完才被发现的，所有指示灯都是绿的。

## 五、不同框架，去哪里找开关

| 你在用什么 | 先找这几处 |
|---|---|
| 自己写的脚本 / cron | 定时间隔、有没有事件触发路径、分页大小、有没有游标（cursor） |
| 框架自带轮询（常见 Agent 框架） | polling interval、是否支持 webhook、记忆是否每次全量重放 |
| 平台官方 bot（飞书/钉钉/Slack SDK） | 长连接或 webhook 开关、事件订阅权限、历史读取频率 |
| 模型调用 | 上下文压缩阈值、会话是否复用、缓存命中、max_tokens |

## 六、一页 checklist

- [ ] 知道自己的日预算
- [ ] 知道今天实际用了多少，在哪看
- [ ] 知道自己最大的那类调用是"拉"还是"推"
- [ ] 有"多久没动静就不再读"的规则
- [ ] 断线补偿还在，而且是强制全量
- [ ] 模型侧上下文有上限（压缩阈值或会话轮换）
- [ ] 改完用**外部指标**复测过
